OpenClaw vs Hermes Agent 对比报告

版本： 2026-04-21
参考来源： OpenClaw GitHub / docs.openclaw.ai · Hermes Agent GitHub / docs.hermes-agent.nousresearch.com

一、功能对比

维度 OpenClaw 🦞 Hermes Agent
定位 个人 AI 助手，本地优先 自改进 AI 代理（内置学习循环）
语言 TypeScript / Node.js Python
安装方式 npm install -g openclaw curl ... install.sh
首次运行 openclaw onboard hermes setup
核心交互 CLI + 桌面客户端 + 消息渠道 全功能 TUI（交互式终端）
消息渠道数量 25+ 个渠道（WhatsApp、Telegram、Discord、Slack、Signal、iMessage、飞书、微信、QQ、WebChat 等） 18 个平台适配器（Telegram、Discord、Slack、WhatsApp、Signal、Matrix、Email、SMS、钉钉、飞书、企业微信、微信、QQ、BlueBubbles 等）
技能系统 Skill（SKILL.md）按文件夹组织，支持 ClawHub 市场 Skill Hub（agentskills.io），支持自动从经验中创建技能
IDE 集成 无 ACP 协议：支持 VS Code、Zed、JetBrains
语音 Voice Wake（macOS/iOS） + Talk Mode + ElevenLabs TTS 语音备忘录转录
视觉界面 Live Canvas（可渲染 HTML/CSS/JS） 无原生 Canvas
定时任务 Cron Jobs（JSON 配置） Cron（自然语言配置，自然语言注入）
子代理/并行 sessions_spawn（隔离会话） delegate 工具（子代理 + Python RPC）
学习循环 无内置 有 — 自动从复杂任务创建技能，技能自我改进，定期推送记忆
批量/研究 无 批量轨迹生成、Atropos RL 环境、轨迹压缩
迁移支持 无 hermes claw migrate 支持从 OpenClaw 导入

功能小结： OpenClaw 渠道覆盖面更广，有 Canvas 视觉界面和本地语音生态；Hermes 的差异化在于内置自我改进学习循环、IDE 集成（ACP）和 RL 研究能力。

二、架构对比

OpenClaw 架构

  • Gateway：单例守护进程，持有所有消息会话（WhatsApp 通过 Baileys 直连）
  • 控制平面：WebSocket 连接（macOS App、CLI、WebChat）
  • Node 架构：macOS/iOS/Android/无头节点也通过 WebSocket 连接，声明 role: node
  • Agent Runtime：内置于 Gateway，基于 Pi agent core
  • Canvas：由 Gateway HTTP 服务器提供 (/__openclaw__/canvas/)

Hermes Agent 架构

  • AIAgent：同步编排引擎（~10,700 行），处理 provider 选择、prompt 构建、tool 分发、重试、压缩、持久化
  • Provider Resolution：统一解析器，映射 (provider, model) → (api_mode, api_key, base_url)，支持 18+ provider
  • Tool Registry：47 个工具，19 个 toolsets，支持 6 种终端后端
  • Messaging Gateway：长进程，18 个平台适配器，统一 session 路由
  • Plugin System：三层发现源（user/project/pip），支持 memory provider 和 context engine 插件

架构差异总结

维度 OpenClaw Hermes
核心语言 TypeScript/Node.js Python
Agent 核心 Pi agent core（嵌入式） 自研 AIAgent（~10,700 行）
会话存储 JSONL 文件（~/.openclaw/agents/<id>/sessions/） SQLite + FTS5（~/.hermes/state.db）
协议层 WebSocket（自研类型化 WS API + TypeBox schema） Python subprocess / WebSocket（gateway）
Canvas/视觉 有（Live Canvas + A2UI） 无
IDE 集成 无 ACP（VS Code/Zed/JetBrains）
部署灵活性 主要本地 可本地/Docker/SSH/Daytona/Modal/Singularity

三、性能 / 并发对比

维度 OpenClaw 🦞 Hermes Agent
运行时 Node.js（推荐 Node 24） Python 3.11+（uv 管理）
并发模型 Node.js 事件驱动 + WS 连接池 同步 AIAgent + 异步 gateway 消息分发
上下文压缩 Session compaction（摘要）+ 工具结果修剪 ContextCompressor（有损摘要）+ Anthropic prompt caching（cache breakpoints）
流式输出 Block streaming（可选，默认关闭，按段落/chunk 合并） 流式 + tool output 实时显示
Token 估算 内置 model_metadata.py（模型 context length 管理）
模型冗余 多 provider fallback 配置 Provider 解析器 + 多 API 模式（chat_completions / codex_responses / anthropic_messages）
空闲成本 需持续运行 Daytona/Modal 无服务器模式：空闲时休眠，几乎零成本
最小部署 需持续在线的 VPS/本地 $5 VPS（明确宣传）
多 agent 多 agent 路由 + 隔离 session（agents.defaults.sandbox） Subagent delegation（delegate 工具，并行工作流）

性能小结： Hermes 在成本优化上更激进（无服务器休眠），OpenClaw 在实时交互上有更精细的流控。Hermes 的 FTS5 全会话搜索在召回历史信息时比 JSONL 线性扫描更高效。

四、记忆对比

维度 OpenClaw 🦞 Hermes Agent
长期记忆文件 MEMORY.md、USER.md、AGENTS.md、SOUL.md、TOOLS.md、IDENTITY.md、BOOTSTRAP.md MEMORY.md（2,200 字符上限）、USER.md（1,375 字符上限）
记忆写入 Agent 手动调用工具写入文件 Agent 通过 memory 工具（add/replace/remove）管理，有子串匹配
容量管理 手动（文件级别，无硬上限） 硬字符上限（2,200 / 1,375），满时拒绝写入，需先整理
会话历史 JSONL 转录（sessions/<id>.jsonl） SQLite + FTS5 全文本搜索（所有 CLI/消息会话）
历史召回 sessions_history 工具（需知道 session ID） session_search 工具（FTS5 + LLM 摘要）
外部记忆 Provider 无 8 个官方插件：Honcho、OpenViking、Mem0、Hindsight、Holographic、RetainDB、ByteRover、Supermemory
用户建模 USER.md（手动） Honcho dialectic（自动跨会话用户建模）
学习循环 无 有 — 复杂任务后自动创建技能，技能自我改进，定期”nudge”持久化知识
记忆注入时机 Session 启动时注入快照（冻结，不随写入改变） 同上（冻结快照，变更在下一 session 生效）
记忆安全扫描 无明确说明 有 — 记忆条目注入前扫描注入/外泄模式和不可见 Unicode 字符
会话链接 session.identityLinks（跨渠道身份关联） identityLinks（未明确公开文档）

记忆小结： Hermes 的记忆系统更结构化（硬上限、安全扫描、外部 Provider、Honcho 用户建模），且有真正的学习循环；OpenClaw 的记忆更轻量、灵活但也更依赖人工管理。

五、安全对比

维度 OpenClaw 🦞 Hermes Agent
信任模型 个人助手模型（单信任边界）— 明确声明不适用于多租户对抗场景 纵深防御模型（七层）
DM 授权 dmPolicy = pairing/open + pairing code + allowlist DM pairing（配对码）+ 平台级 allowlist + 全局 allowlist
危险命令拦截 工具策略（allowlist + ask）+ security audit --fix 43 种危险模式 + 手动/智能/关闭三档审批模式
沙箱隔离 Docker（默认）+ SSH / OpenShell Docker / Singularity / Modal / Daytona（容器即安全边界）
沙箱配置粒度 agents.defaults.sandbox.mode: "non-main" + 工具 allowlist 容器本身即为安全边界，危险命令检查在容器内跳过
MCP 安全 MCP credential 隔离（工具层面） 环境变量过滤 + MCP subprocess credential 隔离
上下文注入扫描 无明确说明 有 — 项目文件 prompt injection 检测
记忆安全扫描 无明确说明 有 — 注入/外泄模式 + 不可见 Unicode
安全审计工具 openclaw security audit（含 --fix 自动修复） hermes doctor
安全文档 详细（docs.openclaw.ai/gateway/security）含形式化验证 详细（43 种危险命令模式明确列出）
YOLO 模式 无 /yolo 切换（绕过所有审批）
自我保护 防止 gateway 自终止 禁止 pkill/killall hermes/gateway
路径遍历防护 无明确说明 Cron 任务存储路径防路径遍历攻击

安全小结： 两者都采用纵深防御，但思路不同——OpenClaw 侧重工具策略和沙箱配置粒度；Hermes 侧重危险命令的细粒度模式匹配（43 种）和审批流程（manual/smart/off 三档）。Hermes 的安全扫描覆盖范围更广（记忆、上下文文件）。

六、综合评价

维度 OpenClaw 更适合 Hermes 更适合
平台 飞书/微信/QQ/企业微信等国内渠道 国际化平台为主
语音/视觉 需要 Voice Wake、Canvas 视觉界面 无需
成本 可接受持续在线成本 需要极低成本/无服务器休眠
记忆深度 轻量、灵活的记忆管理 需要结构化记忆、自动学习、外部记忆 Provider
开发/研究 TypeScript 生态，IDE 友好 Python 生态，RL/研究场景
安全复杂度 多工具、细粒度沙箱配置 危险命令审批、容器隔离为主
自改进 无 有（内置学习循环 + 技能自动创建）
IDE 集成 不需要 需要（VS Code/Zed/JetBrains）

两者定位有显著差异：OpenClaw 是一个本地优先、多渠道、多模态的个人助手，强调本地存在感和实时交互；Hermes 是一个自改进的 AI 代理平台，强调云端灵活性、学习能力和研究友好性。
